# Повернення 50% через LiqPay однією кнопкою

Дата: 2026-11-06. Продовження `2026-10-26-late-cancel-design.md` (правило 50% не змінюється).

## Навіщо

Зараз 50% за пізнє скасування разового персонального / спліту тренер повертає сам у кабінеті LiqPay і натискає «Повернено». Це довго (треба знайти платіж, номера в застосунку немає) і помилково: 04.11 застосунок рахував до повернення 300 ₴ (половина персонального 600), а в кабінеті повернули 425 ₴ (половина всієї оплати 850, де була ще клубна карта).

## Рішення користувачки

- У тренера на «Клієнти» → «Повернути гроші» дві кнопки: **«Повернути»** (застосунок сам надсилає LiqPay запит на повернення) і **«Не списувати»** (пробачити, як зараз).
- Клієнт при скасуванні бачить те саме попередження, що й зараз; нічого не повертається, доки тренер не натисне.
- **Ідемпотентність обов'язкова**: гроші не можуть піти двічі.
- Якщо результат невідомий, тренер може натиснути **«Перевірити»**: застосунок один раз питає статус замовлення в LiqPay.
- Готівка: як зараз, тренер віддає з рук і натискає «Віддала».
- **Повернення належить тренеру тренування** (не тренеру клієнта): лише він бачить рядок у «Повернути гроші» і натискає «Повернути» / «Не списувати» / «Віддала». Це одне рішення (або пробачити, або повернути), і «Не списувати» вже тепер лише його; персональні / спліт він дає тільки своїм клієнтам або клієнтам без тренера.
- Вимкнули тренера, поки повернення чекає: його рядки `DUE` переходять до тренера, якому передають клієнтів (`transferToId` у `disableTrainer`, як готівкові покупки, що чекають).
- Пуш тренеру про скасування (`MEMBER_CANCELLED`) при половині додає рядок «Повернути 300 ₴: Клієнти».

## Що каже LiqPay (документація + тест 04-06.11)

- Запит: `action: refund`, `version: 3`, `public_key`, `order_id`, `amount` (часткове можна). **Ключа ідемпотентності немає**; кілька часткових повернень з одного замовлення можливі, тож повтор = гроші вдруге.
- Відповідь: `result` ok | error, `status` (`reversed` = повернено), `wait_amount` (true = «за рахунок майбутніх платежів», налаштування кабінету, не параметр запиту).
- Callback `reversed` приходить і на часткове: `refund_amount` = **сума всіх повернень** з замовлення, `amount` = вся оплата. При «за рахунок майбутніх» callback приходить, лише коли надійдуть нові оплати (тест: повернення 04.11, callback 06.11), а status API до того показує `success` без повернення.

## Як працює

Стани `cancel_refunds.status`: `DUE` → `SENDING` → `DONE`, або `SENDING` → `DUE` при явній помилці. `CANCELLED` = «Не списувати», як зараз.

**«Повернути»** (`POST /admin/cancel-refunds/:id/refund`, лише онлайн-оплата):
1. Compare-and-set `DUE` → `SENDING` (записуємо `sent_at`, `sent_by`, `payment_id` = оплачений платіж покупки). Хто не виграв, отримує поточний стан (див. «Ідемпотентність»).
2. Status API по `order_id`: `baseline` = `refund_amount` (0, якщо не було). Якщо `baseline` більший за суму наших повернень через застосунок з цієї покупки (`done_via = LIQPAY`), то з оплати вже повертали в кабінеті: **не надсилаємо**, назад у `DUE` з помилкою «з цієї оплати вже повертали, перевірте в кабінеті». Status API недоступний: назад у `DUE`, «спробуйте ще».
3. Сума не більша за залишок оплати (`payments.amount − baseline`), інакше назад у `DUE` з помилкою. Зберігаємо `expected_refunded_uah` = `baseline + amount_uah`, потім надсилаємо refund.
4. Відповідь:
   - `result ok` + `status reversed` → `DONE` (`done_via = LIQPAY`, `done_at`, `done_by`);
   - `result error` або `status error | failure` → `DUE`, `last_error` = `err_code` (у лог `err_description`);
   - таймаут, мережа, не 200, будь-який інший статус → лишається `SENDING` (результат невідомий).

Відповідь (безпечний набір полів) зберігаємо в `liqpay_response`. Відповідь, «Перевірити» і callback змінюють стан лише compare-and-set з `SENDING`, тож хто прийшов другим, нічого не змінює.

Запит у LiqPay йде **поза транзакцією** (стан уже збережено першим compare-and-set), щоб HTTP не тримав блокувань.

**Ідемпотентність:**
- запит refund для рядка надсилається **лише один раз**: тільки той, хто виграв `DUE` → `SENDING`; рядок у `SENDING` застосунок **ніколи** не надсилає вдруге;
- повторне натискання, другий тренер, повтор запиту після втраченої відповіді: 200 з поточним станом (`SENDING` / `DONE`), нового запиту немає;
- `CANCELLED` → 409.

**«Перевірити»** (`POST /admin/cancel-refunds/:id/check`, лише для `SENDING`): status API; `refund_amount >= expected_refunded_uah` → `DONE`; інакше лишається `SENDING`. Повторно не надсилає ніколи.

**Callback `reversed`** (`PaymentService.handleCallback`, оплата PAID): як зараз зберігає `refund_callback`, і додатково рядки `SENDING` цієї покупки з `expected_refunded_uah <= refund_amount` → `DONE`.

**Хто**: `cancel_refunds.trainer_id` = тренер тренування в момент скасування (`training_slots.trainer_id`). `GET /admin/cancel-refunds/pending` і всі дії над рядком: лише `trainer_id = я`, інакше 404 (замість теперішнього `visibleTo`). `disableTrainer` у тій самій транзакції переводить рядки `DUE` на `transferToId`; рядки `SENDING` теж (їх доводить до кінця callback або «Перевірити» нового тренера).

**«Не списувати»** (`waiveCancelFee`): лише поки `DUE`. **Виправити**: зараз рядок у `SENDING` проходить перевірки й пробачення спрацює під час повернення; має бути 409 (`REFUND_IN_PROGRESS`). Для рядка з повернення перевіряти `cancel_refunds.trainer_id` (переданий після вимкнення рядок новий тренер теж може пробачити), для пізнього скасування без повернення як зараз, `trainer_id` слота.

**«Віддала»** (`POST /admin/cancel-refunds/:id/done`): готівкові покупки з `DUE` (`done_via = CASH`). Для онлайн лише з `SENDING`, як вихід для завислого рядка: тренер побачив повернення в кабінеті й натискає «Повернено (перевірила в кабінеті)» (`done_via = MANUAL`). Онлайн з `DUE` → 400. Кнопки «надіслати знову» немає.

## Інтерфейс («Повернути гроші», без слова «LiqPay», без довгого тире)

- Онлайн, `DUE`: «Повернути 300 ₴» (основна) і «Не списувати». Перед поверненням підтвердження в `Modal`: «Повернути 300 ₴ на картку, якою платила Олена?».
- `SENDING`: «Повертаємо 300 ₴…», кнопки «Перевірити» і «Повернено (перевірила в кабінеті)», номер платежу (`liqpay_payment_id`) і підказка «якщо довго, знайдіть платіж у кабінеті оплат → Повернення».
- Помилка: `role="alert"`, текст за кодом (`errorText`).
- Готівка: «Віддала 300 ₴» і «Не списувати».
- `DONE` зникає з блоку; у «Скасували» «повернено 300 ₴», як зараз.

## БД

`cancel_refunds`: статус `SENDING` у `oneOf` (CHECK перестворити вручну, `db:push` старий список не оновлює), нові колонки `trainer_id` (FK `admins`, NOT NULL, індекс; для старих рядків заповнити з `training_slots.trainer_id`), `payment_id` (FK `payments`), `expected_refunded_uah`, `sent_at`, `sent_by`, `done_via` (`LIQPAY` | `CASH` | `MANUAL`, null для старих), `last_error`, `liqpay_response` (jsonb).

## Перевірка в тестовому режимі (до того, як покладатися на кнопку)

- часткове повернення через API: вигляд відповіді (`status`, `wait_amount`), який підпис приймає (sha1 / `version` 3, як status API);
- callback `reversed` після нього і `refund_amount`;
- повторне натискання й два тренери одночасно: один запит у LiqPay;
- «Перевірити» до і після callback.

Відомо наперед: у режимі «за рахунок майбутніх платежів» status API не бачить повернення, доки воно чекає, тож «Перевірити» може днями казати «ще ні», а перевірка «вже повертали в кабінеті» не бачить ручного повернення в черзі. Після активації магазину перемкнути на «з рахунку компанії».

## Рішення, які ухвалила я (перевірте)

- Рядок, що завис у `SENDING` (відповіді немає, callback не прийшов, «Перевірити» не бачить), застосунок сам не розблоковує й повторно не надсилає: тренер дивиться в кабінеті й натискає «Повернено (перевірила в кабінеті)» або, якщо повернення там немає, повертає в кабінеті сам. Кнопки «надіслати знову» немає, бо саме вона дала б подвійне повернення.
- Перевірка «вже повертали в кабінеті» перед надсиланням (крок 2), щоб ручне й автоматичне повернення не склались.
- «Статистика» повернень і далі не віднімає.
- Логи з префіксом `Refund:`, безпечний набір полів, як для інших запитів LiqPay.
