# Власник залу: статистика по всіх тренерах і ціни

## Навіщо

Власник залу хоче бачити, скільки заробляє кожен тренер і зал загалом, і скільки людей ходить до кожного, і сам вирішувати ціни. Тренувань він не веде. Тренери, як і зараз, бачать лише свої цифри, а ціни лише переглядають.

## Підходи

- **Окрема роль власника (вибрано).** Окремий акаунт (пошта + пароль), свій вхід і своя сторінка. Тренерська частина не змінюється: «усі тренери рівні» лишається правдою, власника немає в «Тренерах», його не можна «Вимкнути» і не можна вибрати тренером клієнта.
- Позначка «супер» на акаунті тренера: менше коду, але власник стає тренером (календар, клієнти, розклад, видно в «Тренерах») і з'являється «головний тренер», від якого раніше відмовились.

## Правила

- **Статистика і ціни.** Власник дивиться статистику і **єдиний змінює ціни**. Клієнтів і тренерів не бачить (додати пізніше, якщо треба).
- **Тренер ціни лише бачить**, як клієнт: «Ціни» в меню тренера = той самий серверний список, що `/prices` у клієнта (`PriceList`), без «Змінити» і без «Історії змін».
- **Пошта = лише логін.** Листів немає (сервіс пошти потребує свого домену). Забутий пароль скидає розробник скриптом, як у тренерів.
- **Як з'являється:** `OWNER_EMAIL=… OWNER_NAME=… OWNER_PASSWORD=… npm run seed:owner` створює власника або скидає йому пароль (як `seed:admin`). Реєстрації й запрошень немає. Власників може бути кілька (скрипт з іншою поштою).
- Пароль щонайменше 10 символів, пошта в нижньому регістрі, проста перевірка формату.

## Що бачить власник

Сторінка «Статистика залу», ті самі перемикачі, що в тренера: «Весь час» / «Місяць ‹ ›». **Картка на тренера** (на телефоні без прокрутки вбік), зверху картка «Весь зал»:

```
┌ Весь зал ───────────────┐
│ Разом           41 300 ₴│
│ Прийшло ✓            193│
└─────────────────────────┘
┌ admin ──────────────────┐
│ Абонементи      12 000 ₴│
│ Персональні      8 400 ₴│
│ Спліт            3 000 ₴│
│ Групові          5 500 ₴│
│ Разом           28 900 ₴│
│ Прийшло ✓            142│
└─────────────────────────┘
┌ olena · вимкнено ───────┐
│ ...                     │
└─────────────────────────┘
```

- **Прибуток тренера** рахується як зараз у його «Статистиці» (`StatsService.revenue`): оплачені покупки його клієнтів плюс готівка клієнтів без тренера, яку він підтвердив; за місяцем оплати, за цінами з покупки. Тож цифра тренера тут = цифра в його власній «Статистиці».
- **Покупки без тренера, які ніхто не підтверджував** (онлайн-оплата клієнта без тренера): окремий рядок «Без тренера», щоб «Весь зал» = усі оплачені покупки.
- **Прийшло ✓:** люди з ✓ (і гості) на тренуваннях тренера за період, минулі дні, як «Навантаження» в тренера.
- Вимкнені тренери в таблиці з позначкою «вимкнено»: їхні гроші справжні. Тренер без жодних цифр за період: рядок з нулями (видно, що він є).

## Як

- **Таблиця `owners`:** `id`, `email` (unique), `name` (ім'я для «Історії змін»), `password_hash`, `created_at`. Окремо від `admins`, щоб жоден тренерський запит її не зачепив.
- **Сесії:** `sessions.principal_type` + `owner` (CHECK пересоздати руками, `db:push` його не оновить). `SessionUser` отримує `{ type: 'owner', id, email }`; `AdminGuard` і `MemberGuard` власника не пускають, новий `OwnerGuard`.
- **Вхід — одна форма для тренера і власника**, «Вхід для команди» (так і кнопка на першій сторінці, замість «Вхід для тренера»), поле «Логін або пошта». `POST /auth/admin/login`: значення з `@` шукається серед власників, без `@` серед тренерів (логін тренера `^[a-z0-9._-]{3,32}$`, `@` у ньому не буває). Невдача однакова для обох: «Невірний логін або пароль». Відповідь каже роль, фронт веде тренера на `/admin`, власника на `/owner`. `/auth/me` повертає власника, «Вийти» як у всіх.
- **Дані:** `GET /owner/stats` → `{ trainers: [{ id, username, disabledAt, revenue: { allTime, months }, present: { allTime, months } }], unassigned: { revenue } }`; підсумок «Весь зал» рахує фронт. Розрахунок прибутку винести з `StatsService` у спільну функцію з параметром «один тренер / усі, згруповано по тренеру», щоб цифри не розійшлися.
- **Фронт:** вхід на `/admin/login` (той самий `LoginForm`, варіант `admin`); `/owner` — статистика. Тренер або клієнт на `/owner` → на свою сторінку; власник на `/`, `/admin` → на `/owner`.
- **Ціни:**
  - власник: `GET /owner/prices` (список + «Історія змін»), `PATCH /owner/prices/:id` `{amountUah, expectedAmountUah}` — те, що зараз `/admin/prices`, з тим самим compare-and-set (власників може бути кілька) і попередженням перед збереженням («Ціна зміниться для всіх тренерів і клієнтів»). Сторінка `/owner/prices`, вкладка поруч зі статистикою. Код сторінки переноситься з `app/admin/prices`.
  - `GET /admin/prices` і `PATCH /admin/prices/:id` прибираються. `GET /prices` пускає і клієнта, і тренера; `/admin/prices` стає серверною сторінкою, як `/prices` (спільна функція завантаження і `PriceList`), назад на «Панель тренера».
  - хто змінив: `price_changes.changed_by` і `price_items.updated_by` зараз посилаються на `admins` (NOT NULL у `price_changes`). Додаються `changed_by_owner_id` / `updated_by_owner_id` (на `owners`), `changed_by` стає nullable, CHECK: рівно одне з двох. Старі зміни тренерів лишаються в історії з логіном тренера, нові показують ім'я власника.
  - поки власника не створено, ціни змінити ніхто не може: першим кроком після деплою `npm run seed:owner`.
- **Push і крони** власника не стосуються.
